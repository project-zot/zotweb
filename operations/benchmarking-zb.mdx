`zb` benchmarks a zot registry, or any registry that conforms to the [OCI Distribution Specification](https://github.com/opencontainers/distribution-spec). Use it to:

- Compare configuration changes
- Compare software versions
- Compare hardware or deployment environments
- Compare with other registries

<Tip>
  Install `zb` when you install zot. Run it before you go to production to get a baseline, and again after major changes.
</Tip>

## Get zb

<Tabs>
  <Tab title="Binary">
    Download the executable for your platform from the **Assets** of a [release](https://github.com/project-zot/zot/releases). Binaries are named `zb-<os>-<architecture>`, for example `zb-darwin-amd64`.

    | OS | Architecture | Platform |
    |---|---|---|
    | `linux` | `amd64` | Intel-based Linux servers |
    | `linux` | `arm64` | ARM-based servers and Raspberry Pi 4 |
    | `darwin` | `amd64` | Intel-based macOS |
    | `darwin` | `arm64` | ARM-based macOS |

    You can rename the file to `zb`. This page uses `zb` as the command name.
  </Tab>
  <Tab title="Container">
    Run the released image:

    ```bash
    docker run --net=host -it ghcr.io/project-zot/zb:latest -c 10 -n 1000 http://localhost:8080
    ```
  </Tab>
  <Tab title="From source">
    Clone the zot repository and run `make bench`. Use the same `OS` and `ARCH` you used to build zot. The binary is written to `bin/`. For example:

    ```bash
    make OS=darwin ARCH=amd64 bench
    ```

    This creates `bin/zb-darwin-amd64`. A [sample Dockerfile for zb](https://github.com/project-zot/zot/tree/main/build/Dockerfile-zb) is in the repository.
  </Tab>
</Tabs>

## Run a benchmark

Pass the registry URL and the load you want:

```bash
zb -c 10 -n 1000 -s 127.0.10.0/24 http://localhost:8080
```

This runs every test with 10 concurrent clients and 1,000 requests each, using source addresses from `127.0.10.0/24`.

<Note>
  `zb` rounds the number of requests down to a multiple of the concurrency, and `-n` can't be smaller than `-c`.
</Note>

### Options

```text
Usage:
  zb <url> [flags]
```

<ParamField path="-c, --concurrency" type="integer" default="1">
  Number of requests to make at a time.
</ParamField>

<ParamField path="-n, --requests" type="integer" default="1">
  Number of requests to make. Can't be less than the concurrency.
</ParamField>

<ParamField path="-A, --auth-creds" type="string">
  Colon-separated Basic authentication credentials, as `user:password`.
</ParamField>

<ParamField path="-r, --repo" type="string">
  A repository on the remote registry to use for test data.
</ParamField>

<ParamField path="-d, --working-dir" type="string">
  A directory for test data. `zb` creates a temporary `zb-*` subdirectory there and removes it on exit.
</ParamField>

<ParamField path="-i, --src-ips / -s, --src-cidr" type="string">
  Source addresses to send requests from: a colon-separated list of IPs, or a CIDR block. The two options are mutually exclusive.
</ParamField>

<ParamField path="-t, --test-regex" type="string">
  A regular expression that selects which tests to run. Without it, `zb` runs all tests.
</ParamField>

<ParamField path="-l, --list-tests" type="boolean">
  Print the available tests and exit. With `--test-regex`, list only the tests that match.
</ParamField>

<ParamField path="-o, --output-format" type="string" default="stdout">
  Output format: `stdout`, `json`, or `ci-cd`. See [Output](#output).
</ParamField>

<ParamField path="--skip-cleanup" type="boolean" default="false">
  Leave the pushed repositories on the remote registry after the run.
</ParamField>

<ParamField path="--max-timeout-failures" type="integer" default="0">
  The total number of timeout-related request failures allowed across the run. By default any timeout fails the run. Non-timeout failures always fail the run.
</ParamField>

<ParamField path="-u, --upstream-server-url" type="string">
  The upstream server URL for the sync tests. You must set it to run them. See [Tests](#tests).
</ParamField>

<ParamField path="-v, --version" type="boolean">
  Show the version and exit.
</ParamField>

### Tests

By default `zb` runs the whole suite:

- **Get Catalog**
- **Push Monolith** at 1 MB, 10 MB, and 100 MB
- **Push Chunk Streamed** at 1 MB, 10 MB, and 100 MB
- **Pull** at 1 MB, 10 MB, and 100 MB
- **Mixed** pull and push workloads that blend sizes and operations
- **On-demand Sync** of 100 MB and 1 GB images, which need `--upstream-server-url` and are skipped without it

Run `zb --list-tests` for the exact list in your version, and use `--test-regex` to run a subset:

```bash
zb -c 4 -n 100 -t 'Pull 10MB' http://localhost:8080
```

## Output

By default `zb` prints a summary per test to the terminal:

```text
Registry URL: http://localhost:8080

Concurrency Level: 2
Total requests:    100
Working dir:

============
Test name:            Get Catalog
Time taken for tests: 45.397205ms
Complete requests:    100
Failed requests:      0
Requests per second:  2202.7788

2xx responses: 100

min: 402.259µs
max: 3.295887ms
p50: 855.045µs
p75: 971.709µs
p90: 1.127389ms
p99: 3.295887ms

============
Test name:            Push Monolith 1MB
...
```

Look at **Requests per second** for throughput and at the percentile latencies for tail behavior. A non-zero **Failed requests** count means errors, and `zb` reports the error types and counts.

For CI pipelines, `-o ci-cd` writes the results to a `ci-cd.json` file in the current directory. It holds one entry per test with its requests-per-second value:

```json
[
  {"name": "Get Catalog", "unit": "requests per sec", "value": 2202.7788, "range": "3"}
]
```

<Note>
  The `--help` text lists `json` as an output format. In the current code, only `ci-cd` writes a results file.
</Note>

## Tips for useful results

- Benchmark a registry that matches production: the same storage backend, [deduplication](/configuration/storage/overview) setting, and extensions.
- Run `zb` from a separate machine, or use `--src-cidr`, so the client isn't the bottleneck.
- Repeat runs and compare like with like. Change one variable at a time.
- Use `--skip-cleanup` if you want to inspect the data a run created.

See also [Profile performance](/operations/profiling) to find out where zot spends time under load.
