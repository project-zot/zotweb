zot is an OCI-native container image registry. This page covers its design goals, overall structure, and the main components.

## Design goals

<AccordionGroup>
  <Accordion title="OCI-first" defaultOpen>
    - **HTTP APIs strictly conform to the [OCI Distribution Specification](https://github.com/opencontainers/distribution-spec).** zot aims to be a production reference implementation of the specification. It doesn't implement any other vendor's registry protocol. Docker-format images are accepted through an opt-in compatibility mode on the same API. See [Docker client](/v2.1.x/clients/docker#docker-image-format-compatibility).
    - **Storage follows the [OCI Image Specification](https://github.com/opencontainers/image-spec).** The only supported layout is the OCI image layout. As a result, zot can serve any existing OCI image layout, and it converts data on the wire into that layout.
  </Accordion>
  <Accordion title="Single binary" defaultOpen>
    zot ships as a single binary, and the full binary includes every feature, so deployment is simple on bare metal, cloud, and embedded devices. A single configuration file controls its behavior.
  </Accordion>
  <Accordion title="Enable only what you need" defaultOpen>
    The core OCI-compliant HTTP APIs and storage are separate from add-on features modeled as [extensions](/v2.1.x/concepts/extensions). You can select extensions at build time and at run time. See [Security posture](/v2.1.x/security/posture) for conditional builds.
  </Accordion>
</AccordionGroup>

## Overall architecture

zot is organized as: **zot-full = zot-minimal + extensions**.

- The **minimal build** is the core registry: the Distribution Specification API, TLS, authentication and authorization, rate limiting, image storage with garbage collection, retention and deduplication, MetaDB, and the task scheduler.
- The **full build** adds features outside the specification that the specification allows as [extensions](https://github.com/opencontainers/distribution-spec/tree/main/extensions).

## Components

### External interaction

Clients and administrators interact with zot in two ways:

- **Client-initiated queries** for data and metadata, over HTTP APIs. Core data path queries follow the OCI Distribution Specification.
- **Admin-initiated configuration**.

The standard Distribution Specification endpoints, such as catalog, tag list, and referrers, are always available. With the `search` extension enabled, you can also run GraphQL queries over image metadata. See [Search with GraphQL](/v2.1.x/use/search-graphql).

### MetaDB

zot keeps a metadata database, called MetaDB, for features that need to query images or store state. It's created only when at least one of these is enabled: the `search` extension, basic authentication (which stores user API keys and preferences), image trust, retention, or quotas.

- **Local storage:** MetaDB is a local BoltDB file.
- **Remote storage:** MetaDB uses Redis or DynamoDB. DynamoDB works only with S3 storage. See [Cache drivers](/v2.1.x/configuration/storage/cache-drivers).

### Configuration

One configuration file governs a zot instance. It has sections for `http`, `storage`, `log`, and `extensions`.

For sensitive credentials, you can store values in separate files that the main file references. Separate files let you apply stricter permissions, and they work with [Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/). See the [configuration overview](/v2.1.x/configuration/overview).

### Authentication and authorization

zot supports a full set of authentication and authorization options natively. They're enforced before any request reaches the storage layer. See [Authentication](/v2.1.x/security/authentication).

### Storage drivers

zot supports any modern local filesystem and AWS S3 or S3-compatible storage. It also supports GCS and Azure Blob Storage. See [Storage overview](/v2.1.x/configuration/storage/overview).

<Note>
  On local storage, deduplication uses hard links, so the filesystem must support them. Remote storage uses a cache driver instead.
</Note>

### Security scanning

zot integrates with the [trivy](https://github.com/aquasecurity/trivy) scanner to find vulnerabilities in images. It refreshes the vulnerability database periodically at a configurable interval. The scanner implementation is hidden from you and may change over time. See [CVE scanning](/v2.1.x/security/cve-scanning).

### Background tasks

A task scheduler runs periodic work such as garbage collection, retention, sync, and scrubbing. It's designed not to degrade or interrupt foreground HTTP requests. See [Background tasks](/v2.1.x/configuration/background-tasks).
