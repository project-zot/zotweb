Work through this list before you put a zot registry in front of real users. Each item links to the page that explains how to do it.

<Warning>
  The default configuration of the zot container image is for trying zot out. It has no authentication, no TLS, and a `debug` log level. Don't expose it to a network as it is.
</Warning>

## Network and TLS

- [ ] **Serve over HTTPS.** Set `http.tls.cert` and `http.tls.key`, or terminate TLS at a load balancer you control. Docker requires HTTPS for any registry other than `localhost`. See [HTTP and TLS](/v2.1.x/configuration/http).
- [ ] **Use a certificate from a trusted CA**, such as Let's Encrypt or your organization's CA. Test a public-facing registry with a service such as the [Qualys SSL Server Test](https://www.ssllabs.com/ssltest/). See [Install on Linux](/v2.1.x/install/linux#after-the-installation).
- [ ] **Decide who can reach the registry** and restrict the listener address and network paths to match.

## Authentication and access control

- [ ] **Turn on authentication.** Choose htpasswd, LDAP, OpenID Connect, bearer tokens, or mutual TLS. See [Authentication](/v2.1.x/security/authentication).
- [ ] **Define access control policies** for each repository and decide deliberately whether to allow anonymous reads. See [Access control](/v2.1.x/security/access-control).
- [ ] **Set an `adminPolicy`.** With authentication on, admin-only endpoints such as profiling and trust-key upload need a matching `accessControl.adminPolicy`.
- [ ] **Use API keys or tokens for automation** instead of personal passwords. See [API keys](/v2.1.x/security/api-keys).
- [ ] **Keep secrets out of the main configuration file.** Put credentials in separate files with strict permissions, or use Kubernetes Secrets. See [Configuration overview](/v2.1.x/configuration/overview#keep-secrets-out-of-the-main-file).
- [ ] **Restrict the metrics endpoint** with the `metrics` access policy. See [Monitoring](/v2.1.x/operations/monitoring#restrict-who-can-read-metrics).

## Storage

- [ ] **Pick a storage backend** that fits your scale and durability needs, and put the data on a persistent, backed-up volume or bucket. See [Storage overview](/v2.1.x/configuration/storage/overview).
- [ ] **Choose the right cache driver.** BoltDB supports a single instance. If you run more than one zot instance against shared storage, use Redis or DynamoDB. See [Cache drivers](/v2.1.x/configuration/storage/cache-drivers).
- [ ] **Plan capacity.** Watch free space, and note that `dedupe` needs a filesystem with hard-link support for local storage.
- [ ] **Configure garbage collection and tag retention** so storage doesn't grow without bound. See [Retention and garbage collection](/v2.1.x/operations/retention-gc).

## Run it safely

- [ ] **Run as a dedicated non-root user and group.** zot doesn't need root privileges. For a privileged port, use [systemd socket activation](/v2.1.x/install/linux#systemd-socket-activation) instead of running as root.
- [ ] **Set resource limits.** Use systemd `MemoryHigh`, `MemoryMax`, and `LimitNOFILE` as in [Install on Linux](/v2.1.x/install/linux), or Kubernetes requests and limits.
- [ ] **Pin versions.** Use an explicit release tag for the binary or image, not `latest`, and upgrade deliberately. See [Upgrade zot](/v2.1.x/install/upgrade).
- [ ] **Use the minimal build if you don't need extensions.** It has a smaller attack surface. See [Releases and images](/v2.1.x/install/releases).
- [ ] **Enable only the extensions you need.** See [Enable extensions](/v2.1.x/configuration/extensions).
- [ ] **Don't leave profiling reachable** on a registry without authentication. See [Profile performance](/v2.1.x/operations/profiling).
- [ ] **Review the hardening guidance** in [Security posture](/v2.1.x/security/posture).

## Supply chain security

- [ ] **Verify signatures** if you sign images, using the cosign and notation support. See [Verify image signatures](/v2.1.x/security/signatures).
- [ ] **Turn on CVE scanning** where it fits. It requires local storage. See [CVE scanning](/v2.1.x/security/cve-scanning).
- [ ] **Make release tags immutable** where they must never change. See [Immutable tags](/v2.1.x/security/immutable-tags).

## Observability

- [ ] **Set the log level to `info`.** `debug` is verbose and can slow a busy registry. See [Logging](/v2.1.x/configuration/logging).
- [ ] **Turn on the audit log** if you need a record of who changed what, and keep `log.level` at `info` or `debug` so entries are written.
- [ ] **Collect metrics** with Prometheus, and alert on `5xx` rates and latency. See [Monitoring](/v2.1.x/operations/monitoring).
- [ ] **Wire up health checks.** Use `/livez`, `/readyz`, and `/startupz` for load balancers and Kubernetes probes, or `zot healthcheck` where `curl` isn't available.
- [ ] **Ship logs to a central place** so you can read them after a restart.

## Availability and recovery

- [ ] **Decide whether you need high availability or scale-out**, and set it up before launch. See [Clustering overview](/v2.1.x/operations/clustering/overview).
- [ ] **Back up** configuration, secrets, storage, and MetaDB, and **test a restore**. See [Backup and restore](/v2.1.x/operations/backup-restore).
- [ ] **Write down how to roll back** an upgrade. Don't downgrade without reading the release notes. See [Upgrade zot](/v2.1.x/install/upgrade).

## Validate before launch

- [ ] **Validate the configuration** with `zot verify /etc/zot/config.json`.
- [ ] **Benchmark a baseline** with [`zb`](/v2.1.x/operations/benchmarking-zb) against a setup that matches production.
- [ ] **Test your real clients**, for example Docker, containerd, or Kubernetes, with authentication and TLS on. See [Client compatibility](/v2.1.x/clients/compatibility).
- [ ] **Know where to look when it breaks.** See [Troubleshooting](/v2.1.x/operations/troubleshooting).
